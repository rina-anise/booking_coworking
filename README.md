# Бронирование переговорных - Frontend

Веб-приложение, в котором сотрудник может найти свободную переговорную, забронировать ее и управлять своими бронированиями. Backend (mock-API, WebSocket, тестовые данные) предоставлен вместе с заданием. В backend было внесено минимальное техническое изменение в CORS-конфигурацию: разрешен `DELETE` для возможности отмены бронирований из браузера. Бизнес-логика и API backend не изменялись.

**Demo:** https://booking-coworking.vercel.app/rooms

> Backend развернут на бесплатном тарифе Render и «засыпает» после простоя, поэтому первая загрузка демо может занять до минуты.

## Возможности

- поиск свободных комнат по офису, дате, времени и вместимости;
- страница комнаты с оснащением и расписанием;
- создание и отмена бронирований, раздел «Мои бронирования» (предстоящие / прошедшие / все);
- real-time обновления занятости комнат без перезагрузки страницы;
- время отображается в часовом поясе выбранного офиса.

## Запуск

Требуется Node.js 20+.

Бэкенд и фронтенд - два отдельных процесса, запускать нужно оба.

**1. Backend** (см. `../server/README.md`):

```bash
cd server
npm ci
npm run dev
```

Поднимется на `http://localhost:3000` (REST — `/api/v1`, WebSocket — `/api/v1/ws`,
Swagger-документация — `/documentation`).

**2. Frontend:**

```bash
cd frontend
npm ci
cp .env.example .env
npm run dev
```

По умолчанию откроется на `http://localhost:5173`. Переменные окружения:

| Переменная            | Назначение                            | Локально                        | В production                                  |
| --------------------- | ------------------------------------- | ------------------------------- | --------------------------------------------- |
| `VITE_API_BASE_URL`   | Базовый URL REST API бэкенда          | `http://localhost:3000/api/v1`  | `https://booking-coworking.onrender.com/api/v1` |
| `VITE_WS_URL`         | URL WebSocket-эндпоинта для real-time | `ws://localhost:3000/api/v1/ws` | `wss://booking-coworking.onrender.com/api/v1/ws` |

## Тесты

```bash
npm run test        # прогнать один раз
npm run test:watch  # в watch-режиме
```

Юнит-тестами покрыты:

- `src/shared/lib/time.ts` — вся клиентская валидация границ бронирования (будущее время, лимит 30 дней, рабочие часы 09:00–20:00) и сборка ISO-диапазона из полей формы;
- `src/features/bookings/BookingsPage.tsx` — рендер списка/пустого состояния, переключение вкладок (upcoming/past/all), вызов отмены бронирования.

## Деплой

- **Frontend** — Vercel (Root Directory `frontend`, Framework Preset `Vite`). Переменные `VITE_*` подставляются на этапе сборки, поэтому после их изменения нужен редеплой. Файл `vercel.json` содержит rewrite на `index.html`, чтобы прямые переходы и обновление страницы на `/rooms` и `/bookings` не давали 404.
- **Backend** — Render (Root Directory `server`). Backend хранит данные в памяти и держит WebSocket-соединения, поэтому serverless-функции Vercel для него не подходят. В `CORS_ORIGINS` на Render указан адрес фронтенда.

## Архитектура и технологии

- **React 19 + TypeScript**, сборка — **Vite**.
- **react-router-dom** — маршрутизация (`/rooms`, `/rooms/:roomId`, `/bookings`,
  `/` → редирект на `/rooms`, `*` → страница «Ничего не найдено»).
- **@tanstack/react-query** — работа с серверным состоянием (кэш, `isLoading`/
  `isError`, повторные запросы, инвалидация после мутаций и real-time событий).
  Собственный клиентский стор (Redux/Zustand и т.п.) не использован — данные
  полностью серверные, react-query закрывает эту задачу без лишнего кода.
- **luxon** — вся работа с датами и таймзонами офисов (`office.timezone` из API).
- **Tailwind CSS** — стилизация без отдельной библиотеки компонентов.
- **WebSocket (нативный `WebSocket` API)** — real-time обновления. Обработка подключена глобально в `App.tsx` (`useRealtimeSync`), а не на конкретных страницах, чтобы кэш react-query обновлялся независимо от того, какой экран сейчас открыт.
- **vitest + @testing-library/react** — юнит- и компонентные тесты.

### Структура

```
src/
  api/          — HTTP-клиент и типы ответов API
  app/          — роутер, общий layout, точка входа приложения
  features/
    rooms/      — список комнат, фильтры, страница комнаты, расписание, модалка бронирования
    bookings/   — страница "Мои бронирования"
    user/       — текущий пользователь (мок-авторизация от бэкенда)
  shared/
    ui/         — переиспользуемые состояния загрузки/ошибки/пустого списка
    lib/        — чистые функции (работа со временем/валидация)
  ws/           — real-time синхронизация с react-query
```

### Real-time

Сервер рассылает события всем подключенным клиентам без фильтрации (`booking.created`, `booking.cancelled`, `room.availability_changed`, `data.reset`). `useRealtimeSync` подписывается на сокет один раз на уровне приложения и по каждому событию точечно инвалидирует соответствующие
react-query ключи (`rooms`, `room-schedule`, `my-bookings`) — данные перезапрашиваются автоматически, без ручного обновления страницы.

Переподключение при обрыве соединения и отображение статуса связи — из раздела дополнительных заданий, в этой версии не реализовано. После обрыва данные обновятся при следующем запросе или перезагрузке страницы.

### Принятые решения

- **Клиентская валидация дублирует серверную.** Сервер — источник истины и перепроверяет все ограничения (это указано в ТЗ), но чтобы пользователь не ждал ответа 400 на очевидно некорректный ввод, форма бронирования заранее проверяет: будущее время, лимит 30 дней вперед, попадание в рабочие часы
09:00–20:00. Конфликт бронирования (пересечение с другой бронью) на фронте не проверяется принципиально - это гонка данных, актуальный ответ может дать только сервер в момент создания брони.
- **Фильтры комнат живут в query-параметрах URL**, а не в локальном состоянии компонента — так при переходе на страницу комнаты и обратно выбранные дата/время/офис не сбрасываются, и фильтрами можно поделиться ссылкой.
- **`getCurrentUser` вызывается один раз и кешируется бессрочно**
  (`staleTime: Infinity`) — авторизация замокана бэкендом и не меняется в рамках сессии.

**Минимальное изменение backend.** В предоставленном backend для CORS были разрешены только `GET`, `HEAD` и `POST`, из-за чего браузер блокировал `DELETE /bookings/:bookingId` при отмене бронирования. В `server/src/app.ts` добавлен метод `DELETE` (а также `OPTIONS` для preflight-запросов) в список разрешенных CORS-методов. Остальная логика backend не изменялась.
